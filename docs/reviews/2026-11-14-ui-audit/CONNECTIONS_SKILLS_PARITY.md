# Connections, skills, plugins and agents: required parity

Date: 14 November 2026. Status: planning and source discovery; implementation has not started.

**Every existing Hermes feature family is required in the finished product.** Phasing orders delivery; it does not exclude Messaging, service connectors, skills, plugins, MCP, agent management, artifacts, browser, webhooks, import/export, updates, or other upstream features. The proposed architecture is one unified React/TypeScript application that reuses upstream feature modules and the Hermes backend, with Rust replacing Electron's native bridge. The custom Task view is a useful workspace surface, not the full product.

This inventory is source-verified and static. It is not a claim that all listed functions work in the Rust shell, were exercised live, or existed in exactly this form in the pinned renderer. No live credentials, user configuration, session database, social messages or publication were read or changed during discovery.

## Concepts the redesign must preserve

| Kind | Meaning and ownership |
|---|---|
| Messaging platform | A gateway adapter through which people receive or send Hermes conversations: Telegram, Discord, and other discovered platforms. Includes delivery, access policy, pairing and runtime health. |
| Hosted service connector | A service account/tool connection exposed by the backend catalog. Includes authentication, multiple accounts, aliases, organizational policy and per-tool access. It is not necessarily a messaging channel. |
| Local connector / MCP server | A locally configured or remotely reached MCP tool server, sometimes installed by a plugin. Includes process/HTTP transport, auth, discovery, logs and tool filters. |
| Skill | Instructions and supporting resources loaded by the agent, with provenance, enablement and editing/locking rules. A social-media skill can invoke an external CLI without being a Messaging adapter. |
| Agent plugin | Backend extension or portable Agent Plugins v1 package. May contribute tools, skills, MCP servers, providers, platform adapters or a desktop half. |
| Desktop UI plugin | Renderer extension that contributes panes, settings, actions and other UI. Its loading, native grants and lifecycle differ from backend plugins. |
| Toolset | A group of agent tools with provider/model/prerequisite settings. It is a separate capability family. |
| Profile / persistent agent | An agent's durable configuration and identity. Bot Mode presents profiles as persistent teammates; live delegated subagents are a different concept. |

The current Capabilities shell explicitly contains **Skills, Plugins, Connectors and Toolsets** ([source](/Users/aldrinjoseph/.hermes/hermes-agent/apps/desktop/src/app/capabilities/index.tsx:34)). Messaging is a [separate surface](/Users/aldrinjoseph/.hermes/hermes-agent/apps/desktop/src/app/messaging/index.tsx:151). A common “Add capability” entry point can simplify discovery while preserving these distinct contracts.

## Current Rust compatibility: static gaps

Generic REST and WebSocket transport are useful foundations. They do not establish full-product parity or correct routing.

1. **Profile and connection routing is incomplete.** [Rust connection and socket handlers](/Users/aldrinjoseph/Developer/hermes-desktop-rs/src-tauri/src/commands.rs:428) treat `connection/for` and `ws-url/for` like their unscoped counterparts and ignore their routing arguments. [`hermes:api`](/Users/aldrinjoseph/Developer/hermes-desktop-rs/src-tauri/src/commands.rs:478) always attaches the shell's current home; [`api_call`](/Users/aldrinjoseph/Developer/hermes-desktop-rs/src-tauri/src/commands.rs:98) uses path/method/body/timeout without applying request `profile` or `connection_id`, although [both are declared](/Users/aldrinjoseph/Developer/hermes-desktop-rs/crates/hermes-contract/src/types.rs:71). Profile-scoped connector, skill, plugin and Messaging edits cannot yet be declared parity-safe.
2. **MCP OAuth native support is missing.** [Inventory](/Users/aldrinjoseph/Developer/hermes-desktop-rs/crates/hermes-contract/src/channels.rs:135) contains the callback channels; the [Rust bridge](/Users/aldrinjoseph/Developer/hermes-desktop-rs/src-tauri/src/bridge.js:59) exposes neither `mcpOauth` nor `openExternal`. Remote OAuth cannot complete through the required desktop callback path.
3. **Fleet and remote management is incomplete.** `hermes:agents:roster`, connection registry/config/auth and plugin profile-route channels are inventoried but not implemented by the bridge. [Missing members become absent and event handlers inert](/Users/aldrinjoseph/Developer/hermes-desktop-rs/src-tauri/src/bridge.js:191); that is degraded behavior, not parity.
4. **Native plugin functions are incomplete.** Install/probe/remove, plugin-file grants/operations/revocation/change events and plugin socket grants need their own contracts. Existing readDir/readPluginSource may load local ESM plugins, but that does not cover complete plugin lifecycle or permissions.
5. **Desktop-half reconciliation currently returns an empty success-shaped result.** [Handler](/Users/aldrinjoseph/Developer/hermes-desktop-rs/src-tauri/src/commands.rs:553) always returns `{published: [], refused: []}`. The port ledger labels this channel ported, but installed unified-package reconciliation is behaviorally missing.
6. **Adapters remain backend-owned.** Rust should preserve the gateway contract rather than recreate Telegram or other adapter behavior. Native external links, secure auth/callbacks, local/remote ownership, profile routing and lifecycle still require bridge parity.

Relevant native families include `hermes:mcp-oauth:*`, `hermes:agents:roster`, `hermes:plugin-profile-routes`, `hermes:plugin:installDesktop|probe|removeDesktop|ws-url`, `hermes:pluginFiles:request|grants|op|revoke|changed`, `hermes:openExternal`, and connection configuration/registry/OAuth channels. See the [channel inventory](/Users/aldrinjoseph/Developer/hermes-desktop-rs/crates/hermes-contract/src/channels.rs:1) and [coverage ledger](CHANNEL_COVERAGE.md). Request refusal and absent push events are different gaps.

## Setup flow: simplify presentation, retain the contract

1. Choose the target **agent and connection** before setup; retain that owner for the complete flow, including OAuth cleanup and background actions.

4. Test the actual selected transport and account. Distinguish saved/configured, authenticated, runtime-connected, tools-enabled and usable-in-this-chat.
5. Show the honest activation result: live now, next chat, reload/restart needed, missing dependency or failure, with recovery.
